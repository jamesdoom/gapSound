# Training sessions and day rollover

Daily objectives belong to the browser's local calendar day. An open page updates its clock every second, reloads workspace data when that day changes, and refreshes on window focus or returning to a visible tab. Previous-day objectives remain in SQLite; they are neither copied nor deleted at midnight. Until the new day's data arrives, previous-day objectives are hidden. Unsubmitted objective text is preserved.

Only one unfinished session is allowed by the database. Its original UTC start time survives page reloads and server/process restarts, including sessions older than seven days. Start requests do not replace an existing session. Midnight does not stop, split or restart a session. Closing the browser does not automatically stop it.

Use **Stop session** to finish at the server's current time. If you forgot to stop, open **Recover a forgotten session**, enter the actual end in local time, and choose **Finish recovered session**. The browser converts the chosen time to UTC. The server requires the matching active UUID and an end between the original start and server time. Stale controls cannot stop a different session. Recovery preserves the start and records the selected end; it does not invent activity or delete history. Completed records cannot be edited in this update.

Elapsed time includes time away while the timer was unfinished; the app cannot infer when you stopped studying. Only completed duration counts toward the weekly goal. The last-seven-days total uses a rolling 168-hour UTC window, clips sessions crossing the window boundary and aggregates all completed overlaps independently of the 1,000-item history display limit. Unfinished sessions are prioritized in that list. Totals round down once to whole minutes. The history and total are separate reads; a concurrent completion can appear on the next refresh.

The original recovery/rollover change required no migration; reusable plans below require migration 0009. Routine tests use isolated data and make no live feed requests. Restart verification launches separate Node backend processes against the same temporary SQLite file; browser tests verify reload recovery and a simulated midnight in America/New_York. Full application restart and backup/restore regressions now cover the implemented workflows; native assistive-technology signoff remains a separate acceptance task.

## Reusable objective plans

Daily Training → Reusable objective plan lets you add, edit, remove and reorder up to 20 distinct titles (1–200 trimmed characters each). Save the plan, then choose Apply saved plan to today. Unsaved changes disable application; failed or stale saves preserve the editor draft. Reload saved plan explicitly replaces that draft with the latest saved version. Plan settings persist across reloads, application restarts and backup/restore.

Application is explicit, once per local calendar day, and appends new unchecked objectives in plan order after any existing one-off objectives. Reads, startup and midnight never create objectives. The server verifies the submitted day against the supplied IANA time zone and its current clock; stale-day application is rejected. Editing or clearing the reusable plan affects future applications only, even if today’s plan has not yet been completed. A day already marked as applied cannot apply a revised plan again; add one-off objectives for any extra work. Identical one-off titles are not automatically merged.

Each day retains its copied titles, order and completion state. Existing legacy objectives retain their title, ID, day and completion state during migration and receive position zero; ties use ID order. New objectives append after them. Both one-off additions and plan application enforce a shared limit of 100 objectives per day; application and its daily marker commit atomically. Saved briefings remain immutable, while generation/regeneration captures the currently recorded daily checklist in its stored order. Saving a reusable plan alone does not change a briefing or add objectives to it.

Migration 0009 adds the reusable plan, revision/daily application records and checklist ordering. Run npm run db:migrate before restarting an updated checkout. This remains manual planning; no automatic recurrence, scheduler or spaced-repetition engine was added. Editing already-applied daily titles or reordering historical records is not offered.
